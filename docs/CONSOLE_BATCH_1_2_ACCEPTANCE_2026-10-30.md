# Octalve Cloud — 30 Oct 2026: Batch 1 acceptance and Batch 2 implementation handoff

## Ground truth and screen findings
Authenticated user-provided screenshots of Octalve Console show: customer detail's floating Back/Refresh controls, a generic Amount tile instead of actual identity/account context, customer editor with blank name due to `name` vs Django `full_name`, incorrect phone mapping, a mutable Balance form field with mojibake currency placeholder, and Admin Settings sections consisting of topic labels instead of global configuration editors. These are observed screenshots, **not an authenticated 810-route test run**.

**Batch 1 deployed scope, after GitHub review:** Client Orders and Invoices use shared `RecordDirectory` in desktop and mobile, including status tabs, search, filter dialog, page control and per-row exact detail link. Admin Team, Transactions, Service Billing and Audit Logs use `AdminGenericDirectory` as a compatibility adapter to the same shared presenter. `RecordDirectory` still filters the authorized records *returned in the current API response* for these surfaces; no claim is made that all server records are paged. Admin Customers alone already uses explicit Django server-wide pagination.

### Customer identity and financial authority
- Customer create uses exact backend fields (`full_name`, `email`, optional `username`, `password`, `phone_number`, address and company); customer edit uses the actual `full_name`, contact, address, tax details, notes and explicit status choices. The saved email is displayed, not silently overwritten.
- Customer detail shows real `CustomerDetailSerializer` profile fields, verification status, note, invoice summary, order/service counts and ledger-backed wallet balance. No invented Amount or development-copy summary panel.
- Wallet balances masked by default on Client overview, wallet view and Admin customer detail. A user can reveal and re-hide them; this does not change server privacy permissions.
- Customer profile cannot adjust wallet balance; backend explicitly refuses `balance`, `wallet_balance`, `role`, `is_staff`, `is_superuser` and any unknown PATCH field. Never restore these generic writes.
- `suspended` is distinct from inactive, based on trusted `metadata.account_suspended` and `is_active=false`, and is denied sign-in. This is account access control; overdue invoices belong to billing status separately.
- **No Paystack/Flutterwave wallet funding is represented as ready.** Existing hosted payment flow accepts an exact invoice identifier. Ledger posts are protected, manual balance adjustment is disabled. A wallet top-up requires a separate finance batch: immutable amount+currency quote, gateway-specific signed webhook, independent server verification, locked idempotent `WalletLedger` posting, refund/chargeback/reversal, anti-fraud, reconciliation, and E2E test fixtures. Never credit a wallet from redirect claims or frontend forms.
- **No ad hoc Staff promotion via Customer PATCH.** The current backend model has a single `role` and the legacy update deletes the `ClientProfile` on promotion; this is incompatible with dual-role account preservation. Security-approved implementation must use additive role grants/entitlements, verified MFA step-up, dual-workspace signed server-side selection, token/session rotation, least privilege and revocation. Never infer roles from profile strings or show workspace switching to unauthorised users. Admin/Staff issuance must not be driven by editable client forms.

## Batch 2 — Functioning global Console settings (user-approved design brief)

**Repository:** `octalve-core/octalve-console`, continue strictly from validated post-Batch-1 main. **Source of truth:** Django+Neon for settings; never localStorage or frontend fake state. **Architecture:** Settings = Console operator and public experience policies; Integrations = third-party connection configurations, adapters and secret custody; Provisioning = only execution of vendor tasks based on verified entitlements; Catalogue = commercial publication. Do not move credentials into generic Settings.

### SET-01 — Policy authority and Settings UX
Audit all Settings routes, Django `settings_registry` and existing admin APIs/models, role permissions and audit trails first. Produce endpoint/schema matrix of real GET/PATCH behavior. Create one modular Settings form system with server-fetched values, dirty-field PATCH, field-level validation, concurrency control/versioning, confirmation, reload, errors, disabled states and audit receipts. Store only actual approved keys with server allowlists. Use searchable sections and short, production-friendly guidance; remove empty topic-only cards and dev commentary. Never expose secrets. Match existing Octalve Invoice density and 320/360/390/768/1024/1440 widths.

### SET-02 — General, Security and Theme
General: configured public URLs and brand identity, localization and time zone where backend supports them, support business contacts and public exposure booleans. Security: verified CAPTCHA policy and trusted origins/proxies (never arbitrary client-configured allowlists), MFA session policy, rate limits, without disabling mandatory minimum controls. Theme: persist validated colour/token choices, light/dark preference, logo selections and preview/rollback, emit usable CSS variables while protecting contrast and Octalve identity.

### SET-03 — Invoice policy and Tax
Invoice Settings (distinct from the Commerce invoice list): prefix/next-number policy with unique atomic numbering, customer-visible terms, due-date policy, reminders, tax display, footer and approved versioned Template 01 selection (future templates isolated in `billing/invoice-template/`). Never retroactively mutate issued invoices. Tax: region/currency rates, effective dates, exemptions, disabled/enable windows and immutable invoice snapshots, all server validated and reflected by pricing/checkout calculations; avoid blind arbitrary percentage editing or legal compliance claims.

### SET-04 — Event-driven email templates and outbox
Inventory existing `notifications`, `settings_registry`, email-template API, event sources and sender adapters. Create versioned, seedable editable templates (per-person greetings using strict variables, orders, payment success, invoice issued/due/overdue, domain expiry ICANN windows, support events, season greeting, promotions, broadcast). Allow duplicate, draft, activate/deactivate, preview with sanitised sample, locale and HTML/text bodies. Safe variable syntax and whitelist (`{{customer.first_name}}`, `{{invoice.number}}`, etc.), HTML autoescape and no secrets. A/B or other experiments not needed.
- Never render templates as executable JS or unescaped HTML. Do not allow arbitrary SQL/URL-based recipients or SMTP headers.
- Recipient consent, unsubscribe, suppression lists, rate limits and admin approvals for bulk campaigns.
- Durable outbox with uniqueness key, retry/backoff, dead-letter queue, receipts, per-attempt events, operator replay and dashboard for Pending/Sent/Failed/Suppressed.
- Multiple sender adapters (SMTP, configured email API providers) are kept in Integrations. Settings selects a *verified* default sender and explicitly ordered, healthy fallbacks; never automatically fail over ambiguous non-idempotent sends without delivery-state reconciliation.
- Do not claim emails sent without provider acceptance/receipt; maintain auditable outbox integrity. Separate transactional and marketing mail policies.

### SET-05 — Social sign-in and API keys
Audit active five-screen auth architecture, OAuth callback/session BFF and existing MFA/secure Integration Store. Social providers Google, Apple and Facebook are supported only after specific OAuth/OIDC adapters, callback `state`/PKCE/nonce, issuer/audience/JWKS validation, verified email and account-linking proof. API credentials in protected Integration Store only, never rendered back in Settings; Settings may select and enable only verified approved providers and display their health. Hide unconnected social buttons. Extendable provider registry allows more later.
Clarify API Keys as *Octalve-issued* scoped, rotatable client/staff API credentials **only if** service-to-service authorization is approved; otherwise remove the empty Settings section and link to Integrations for third-party tokens. Require expiry, revocation, last-used/audit, scope checks and MFA step-up where issuance is enabled.

### SET-06 — Other global sections and acceptance
Assess notifications/public messaging, credits as policy only (no manual wallet funds), cron and billing schedule policy (no unverified execution), support contact availability and public feature visibility. Prefer disabled/linked verified controls over placeholders. Test role/tenant boundaries, malicious field injection, concurrency, cross-site request forgery, MFA/security settings privilege changes, GDPR/consent, template injection, signed webhook replay, delivery dedupe, tax-effective dates, invoice numbering collision and readback integrity.

**Gate and deployment:** Discrete commit/test-reviewed PR, full frontend and Django/Postgres security suites. No invented readiness. Owner-approved live operator tests for Settings; record screenshot and behavior at all six widths. If approved, merge to main and perform a single explicit Production deployment of Console + API at one GitHub SHA (Preview disabled). Run health, authorization, invoice and notification smoke and preserve rollback.
