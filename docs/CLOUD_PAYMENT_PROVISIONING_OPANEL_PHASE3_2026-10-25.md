# Octalve Cloud — Phase 3 / payment-to-provisioning + OPanel acceptance

**Status:** Development-only, dependent on draft PR #13 A1/A2. No money collected; no provisioning executed; ONE new OPanel bridge migration proposed (not applied to Production), no authorised Production deployment or database changes. CI uses isolated databases.

- Financial authority: `provisioning.authority.evaluate_payment_to_provisioning` is a **side-effect-free** preflight requiring matching invoice/order/transaction customer, currency and totals; fully paid invoice with timestamps; active non-test gateway; successful transaction; verified notification plus server-validated provenance. A forged `invoice.status=paid`, browser redirect, admin manual payment or test-mode gateway does not qualify.
- This function is **not yet wired to settlement** because all gateway settlement endpoints deliberately remain 503. A future adapter must verify Paystack/Flutterwave signatures plus independent gateway API lookups and record transactional, replay-safe settlement and provenance. Only then may the durable outbox stage provisioning; never trigger from a customer's HTTP response.
- Worker: no external provisioning is performed. Next subphase must implement idempotent task creation, an audited leased worker, WHM `createacct`/DA counterpart, provider confirmation and compensation on timeout; do not convert pending orders to active merely from queue acknowledgement.
- OPanel: per-service owner-scoped read-only overview route `GET /api/services/opanel/:service_id/overview/`, with `/client/services/:id/opanel` frontend. No secrets or server identifiers. Usage shows existing historical snapshots if available and never falsely describes stale data as live. Management tools are honest unavailable states pending account-scoped vendor adapters. No WHM root/admin API token is sent to frontend.
## Confirmed OPanel login authority (owner decision, 25 October 2026)

- **One customer login**: Octalve Console authenticates and registers the customer. The separate `octalve-core/octalve-opanel` application MUST NOT require an additional OPanel customer password, registration, or password reset.
- Console `Manage hosting / Open OPanel` is permitted only for the exact customer-owned, active hosting service **after independently verified successful provider provisioning**. A stored `provider_identifier` or `service.status = active` alone cannot prove provisioning or grant OPanel access. A URL/service ID never grants authority.
- Once integrated, Console grants a short-lived one-time authorization code for OPanel to redeem **server-to-server** with audience, service and client binding and replay protection. OPanel creates its **own independent Secure, HttpOnly session**; Console's session cookie, JWT signing secret and client password are not shared with OPanel.
- Before every provider operation, OPanel revalidates that subject and service remain entitled. Revoked, expired, suspended, terminated, unprovisioned or cross-customer access fails closed. Provider connections and DirectAdmin/cPanel/WHM hosting credentials remain strictly server-side.
- **Current implementation status**: Console now has a testable cross-product SSO issuer, single-use code exchange and fresh entitlement endpoint; OPanel owns the callback/session implementation in its separate PR #1. These are development-only, and no real provider-backed hosting binding has been recorded or qualified for Production. The existing `/client/services/:id/opanel` page is only a read-only **Console-hosted prototype**, not the independent product. The customer-facing Console action now reads `View hosting status` and routes to `/client/services/:id/hosting-status`; the old route is left as a compatibility view. Do not claim that `Open OPanel` works until SSO is implemented and security-tested.
- Owner-approved independent OPanel design contract lives in `octalve-core/octalve-opanel` PR #1. Its other proposed technology choices remain subject to individual acceptance.

- Domain order, registrar, independent authoritative DNS and SSL remain separate future phases; service ownership must be established before any DNS zone mutation. Admin-console commercial authority and OPanel technical authority stay separated.
- Current Vercel connector cannot list or access both Cloud Vercel projects under octalve-vault; GitHub status for previously blocked merge still says rate-limited, which is historical. Do not create an unqualified deployment to probe quota.
- Acceptance: Django no-money authority tests, own-user vs different-user OPanel access, no credentials exposed, frontend typecheck/build, negative states. This is the **first safe thin slice**, not commercial go-live.

## Phase 3B — development integration implemented on draft branches

**Console confidential-client endpoints** (under /api/integrations/opanel/v1/):
- POST /authorize/ — JWT authenticated Console customer through first-party same-origin BFF, with exact owned service authorization; returns fixed registered redirect URI and one-time code, expiry 60 seconds.
- POST /exchange/ — confidential OPanel client only; exact registered callback + PKCE-S256; atomic consumption with fresh entitlement check.
- POST /entitlement/ — confidential OPanel client only; revalidates subject, service, provider binding, status, term and provider confirmation. Fails closed.
- All endpoints default disabled with OPANEL_ISSUER_ENABLED=false. Configure OPANEL_CLIENT_SECRET (at least 32 chars), OPANEL_CLIENT_ID, OPANEL_CALLBACK_URL (exact HTTPS) and require verified provisioning.
- New opanel_bridge.0001_initial migration adds a private VerifiedHostingBinding authority record and hashed OPanelLaunchGrant; no new customer password, JWT-key sharing or provider credentials exposed.
- **Provider confirmation boundary:** active service/provider_identifier alone cannot qualify. A separate provider-api-readback binding with matching account fingerprint, provider ID and sufficiently recent confirmed_at must exist. NO public endpoint creates such a proof; only a future accepted provider-readback worker may do so. This protects Production while provisioning remains disabled.
- Console hosting-status route conditionally exposes external launch only after issuer eligibility; authorize-opanel is customer confirmation page. The BFF allows only browser-bound authorize; confidential endpoints cannot be proxied by customers.

**Independent OPanel implementation:** Its initial Django service implements auth/start, auth/callback, api/session, auth/logout with own database-backed HttpOnly session, PKCE/verifier and state stored server-side, session rotation, idle/absolute expiry and per-request revalidation. It deliberately has no customer registration/login database and no vendor mutation capability. First UI is a read-only secure session landing screen, not the finished hPanel-like experience.

**Release gates:** Provider proof issuer from genuine test-account readback, OPanel hostname and credentials, Console + OPanel exact callback matching, live browser SSO/role/revocation checks, controlled Review deployments, explicit Production approval. CI alone is insufficient to deploy. Console CI disposable PostgreSQL expects historical 49 + catalog 1 + OPanel bridge 1 = 51 migrations and 92 + 2 + 2 = 96 public tables; this is NOT the Production ledger.
