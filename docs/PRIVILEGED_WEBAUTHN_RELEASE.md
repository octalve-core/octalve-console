# Privileged Console WebAuthn

The privileged WebAuthn requirement defaults off. This branch implements the password-to-passkey login exchange, credential and single-use challenge persistence, assurance checks on privileged access and refresh, and a closed boundary around Django admin and Django REST Framework session login when enforcement is enabled.

The Console origin is https://console.cloud.octalve.com and the relying party ID is console.cloud.octalve.com. The browser and verifier require user verification. The backend issues a privileged JWT only after the pinned verifier checks the assertion and updates the credential counter. The signed token identifies its credential and stops working if that credential is revoked. No passkey private key is stored.

## Enrollment and recovery

A deployment operator with an independently approved identity and change reference uses the Django management command `issue_privileged_passkey_grant` with `--account-id`, `--approval-reference`, and `--confirm-independent-approval`. Use `--recovery` only for an approved lost-credential recovery. Approval is an operational control and the command records its reference. It cannot verify the external approval workflow.

Deliver the 15-minute setup code over the approved private channel. The operator visits `/login?passkey=setup` on the canonical Console and provides the code and their current account password to complete the browser ceremony. Store no codes in tickets, chat, CI logs or database plaintext. A new grant invalidates unused earlier grants. Recovery changes old credentials and token revocation only after a valid replacement credential is registered. Issue a separate normal grant for each backup authenticator.

## Production activation gate

Both `CLOUD_PRIVILEGED_PASSKEY_ENROLLMENT_ENABLED` and `CLOUD_PRIVILEGED_WEBAUTHN_REQUIRED` default off.

1. Confirm the database identity, obtain the migration approvals and verify backup and recovery, then apply the additive credential, challenge and enrollment grant migrations.
2. Enable enrollment only. Use independent authorization to enroll the primary and backup authenticators of each privileged operator. Confirm loss recovery and prior credential and JWT revocation on a dedicated test account.
3. Verify the actual browser ceremonies, negative origin and replay handling, and ordinary client login. Schedule cleanup of expired grants and challenges and verify retention of the audit records and approved recovery notifications.
4. Enable mandatory sign-in only after privileged operators are enrolled and the recovery process is proven. Decide whether to keep raw Django admin and DRF session login disabled or qualify a separate passkey flow for them. Under enforcement this code blocks them.

Fixture verifiers and default-disabled deployment do not establish browser or operator readiness. Do not insert production credential public keys manually as a substitute for enrollment.


## AUTH-01 hardening and qualification

- Mandatory enforcement remains default-off. Enrollment-only mode supports explicit sign-in at `/login?passkey=verify` for privileged accounts, using password plus an enrolled authenticator. The API never falls back to password-only on that request; the BFF requires the server's verification confirmation before setting cookies. Normal sign-in is unchanged until enforcement is enabled.
- Basic and Django session authentication cannot satisfy mandatory privileged MFA. Passkey-bound JWTs are checked against active credentials even when enforcement is subsequently disabled. Recovery re-salts the verified current password (without changing its value), invalidating previous Django sessions and password-reset links; tracked JWT families are blacklisted. Untracked legacy bearer tokens must be allowed to expire before declaring full revocation (access lifetime 60 minutes).
- Register a genuinely separate backup authenticator, not merely another device synced to the same passkey. Enrollment excludes previously registered credential IDs. Test primary and backup independently; after recovery enroll a new backup.
- Independently verify identity and change approval outside the management command. Record only the approval reference and safe evidence (account ID, credential count, event timestamps, response status); never capture setup codes, passwords, JWTs, cookies, or raw credential evidence. Send enrollment/recovery notifications over the approved independent channel and record delivery. No automatic mail is implied.
- During enrollment-only mode password-only privileged login is deliberately still available; recovery revokes previous sessions but does not prohibit a new password login. Mandatory enforcement is a separate owner-approved operation.
- Read the [protected production release runbook](CLOUD_PRODUCTION_RELEASE_RUNBOOK_2026-10-26.md) for backup, environment identity, staging and rollback policy. From the existing local checkout use `git fetch origin`, inspect a clean worktree, `git switch main`, then `git pull --ff-only origin main`. Verify the approved SHA before connecting to Production. Run `showmigrations accounts`, `migrate accounts 0005 --plan`, `sqlmigrate accounts 0004` and `sqlmigrate accounts 0005` with the verified Production environment; do not print secrets. Stop if the plan differs from exactly the two additive migrations or if backup/restore is unqualified. Only after owner approval run `python manage.py migrate accounts 0005 --noinput`. Never run tests against Production.
- Retain audit events, expire grants/challenges on schedule under the approved retention policy, and qualify individual credential management separately. No database downgrade is required for a compatible flag rollback. Disabling enforcement is a security downgrade requiring owner approval; keep passkey credential validation active and do not roll back to a build that lacks that validation if passkey sessions have been issued.

For enrollment and qualification use a signed-out or separate private browser window (the ordinary auth-entry route redirects signed-in users to their dashboard). The server records successful passkey login with an internal credential record ID for primary/backup distinction, without logging raw credential evidence. The tests include real cryptographic software assertions as well as mocked enrollment verification; neither is a substitute for physical-device evidence.

## AUTH-02 local guarded migration runner

Use `scripts/plan-neon-production-webauthn.ps1` from clean, already-existing local main at the exact owner-approved SHA, with `-ApprovedCommit <SHA>` and optional `-PostgresBin <absolute path>`. `-Preflight` reads the Production target and checks the entire migration graph (64 migrations / 117 tables); it never applies. `-BackupOnly` creates a fresh custom archive and performs a SCRAM-protected, loopback-only independent full restore, checks all three target tables absent and matches the exact migration ledger digest, then exits without applying. Backups require operator-attested encrypted, access-restricted storage. `-Apply` is separately approved, repeats the backup and restore to ensure freshness, verifies exact source and ledger, and requires the typed phrase `APPLY WEBAUTHN 0004 0005 TO OCTALVE PRODUCTION` before mutation. Both additive migrations run in one outer PostgreSQL transaction; an ambiguous failure is never automatically retried. Independent readback expects 66 migrations / 120 tables, three empty WebAuthn tables and required constraints/indexes. No flag changes, no provider calls or financial mutation. Never share archives, passwords or database URLs.

The guarded schema-only executor holds a transaction-scoped advisory lock on the same Django PostgreSQL connection as both migrations, checks schema and ledger before commit, and performs separate TLS readback afterwards. It does not invoke unrelated application post-migrate receivers. New internal passkey models do not require Django Admin permissions for their Console operations. Protected storage is an operator attestation, not an automatic disk-encryption measurement.

## AUTH-03B passkey management and request budgets

The login network budget is unchanged. A valid two-minute server-signed continuation, bound by keyed HMAC to the exact already-verified password, identifier and challenge, can use a separate eight-request identity budget; forged, missing or mismatched tickets still consume the original password budget. The verifier still checks the password, current account state, credential, RP, origin, signature and one-use challenge. Legacy clients retain the previous budget. No continuation is a session token. The browser respects Retry-After and does not automatically retry. Duplicate credential exclusion remains unchanged.

Admin Settings / Security and Staff Security show only the signed-in operator's safe credential metadata and successful sign-in evidence. Distinct verified record counts do not certify physical independence. Individual revocation uses the existing operator-only authorization boundary: `revoke_privileged_passkey --account-id ID --credential-record-id ID --approval-reference REF --confirm-independent-approval --confirm-surviving-authenticator-and-notification`. The operator must independently confirm physical access to a surviving authenticator and deliver an out-of-band notification; the command checks successful sign-in evidence for another active credential and cannot revoke the last one. Revoked credential-bound access and refresh are denied; unrelated sessions are preserved. No automatic notification is claimed. Lost-all-factor recovery remains separate. No production mutation or enforcement change is part of this code release.

The proposed retention procedure is `prune_privileged_passkey_ceremonies` (dry-run by default); `--apply --approval-reference REF` removes only expired ceremony records older than seven days, bounded per table. Retain all credential and audit records. No schedule or production deletion is authorized until the owner approves the retention policy and qualified execution mechanism.

## AUTH-03C recovery and operational readiness

First qualify using the disposable PostgreSQL CI test `accounts.test_passkey_recovery_readiness`. It creates a non-superuser Staff-role drill account, an unrelated owner fixture and ordinary client exclusively in the test database, uses real synthetic P-256 registration and assertions, tests wrong-origin rejection, recovery, stale challenge invalidation, access/refresh/session revocation, unaffected owner and ordinary client sign-in/refresh/logout. This is not a physical browser drill. Never run Django test commands against the Production database.

For a real-device drill, prefer a separate isolated review environment with a separately reviewed exact RP/origin and no production credentials, providers, payments or provisioning. The current RP is hard-coded to the canonical production Console, so real-browser review environment routing needs a separate reviewed implementation; an ordinary Staff role is NOT a restricted production test account. Do not create a production drill identity until a fail-closed route/role containment design and account creation scope are separately approved. Do not use account 3 for a destructive recovery qualification. Keep enrollment enabled and enforcement disabled until independent owner backup, recovery and client acceptance are complete.

Before an actual recovery issue the grant only after independent identity approval and verified out-of-band notification delivery: add `--recovery --notification-reference REF` to the existing grant command. Record opaque nonsecret ticket/delivery references, not message contents or credentials. Once replacement succeeds, independently verify the exact recovery audit ID, credential record, revocations and account scope; send a post-recovery notice over the separately approved channel and record its receipt using `record_passkey_recovery_notification --account-id ID --recovery-audit-id ID --approval-reference REF --notification-reference RECEIPT --confirm-independent-delivery`. The receipt is an operator attestation, not independently verified email delivery. Notification command is idempotent and sends no mail. Untracked pre-rollout JWT expiry remains a separate gate. Do not automatically retry recovery. The cleanup command now writes a minimal maintenance audit event on an explicitly approved apply, retaining credential and audit history. Seven-day cutoff remains proposed pending retention approval.
