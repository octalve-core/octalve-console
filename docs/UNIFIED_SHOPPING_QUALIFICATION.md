# Unified shopping integration qualification

Baselines: Console `f595b4beb6859faa7d6a0d5ee52356f47f4b26ec`; storefront `858d41637158e83b267a8c4fc92bd2836696b416`.

| Reuse | Integration |
| --- | --- |
| Django `orders.Cart` model and existing unique session key | Guest rows use an opaque host-only shopping credential; account rows use a separate derived key and verified ownership. |
| Published catalogue, registrar route and checkout serializer | Browser submits selections only. The server resolves prices and revisions and verifies availability on domain addition. Existing order and payment controllers still price and validate at checkout. |
| Approved native drawer, cart rows and review | One storefront provider holds live response data above route changes. Existing service cards and legacy Console links remain available when the API gate is off. |
| Console session BFF and checkout routes | Console exchanges its authenticated short-lived claim grant with the API over the API's host-only guest cookie. An atomic merge preserves existing server selections, consumes the grant and deletes the guest row. |

## Contract

All routes are under `/api/orders/shopping/`. The unified flag defaults off. Prices are indicative until canonical order review. No taxes or totals due are made up on the storefront.

- `guest/`: exact storefront Origin. GET reads the current guest snapshot. POST adds `{kind:"domain",domain}`, `{kind:"service",plan,cycle,revision,domain?}` or `{bundle:[domain,...]}` (up to four). DELETE removes `{id}`. The anonymous cookie is Secure, HttpOnly and same-site, expires in 24 hours, and contains no Console credential.
- `account/`: authenticated Client via Console BFF. GET reads; POST adds `{selections:[...]}`; DELETE removes `{id}`.
- `grant/`: authenticated Client POST via BFF for a one-use claim grant valid for 45 seconds.
- `claim/`: exact Console Origin POST `{grant}` with the guest cookie. Merges eligible selections, allowing existing account selections to take precedence, and consumes the guest state.
- `PATCH guest/` and `PATCH account/` accept `{id,domain,register}`. For an existing selection, the domain must be in the cart or an active domain owned by the authenticated client. An empty domain clears the configuration. New registrations are checked through the registrar before the cart transaction. The service and registration selection are committed together.
- Authenticated snapshots include up to 100 eligible domain names in `domains`. Anonymous snapshots contain an empty list.
- Cart responses include `{lines,subtotal,currency}`, with server-priced `{id,selection,kind,name,ready,currency,amount,period,renewal?,setup_fee?}` lines. An invalidated line remains visible for removal. A subtotal is available for ready same-currency lines only. An empty claim can return `{lines:[]}`.

## Session bridge qualification candidate
The fixed Console endpoint /api/shopping/session accepts only the exact storefront Origin, using existing host-only Console cookies. It forwards only approved shopping methods to /api/orders/shopping/storefront-account/ with the access identity and unrevoked refresh proof server-to-server. No JWT or refresh credential is returned, no shared domain cookie is introduced, no cookie is rotated by this bridge. A non-authorizing opaque session fingerprint must match on writes; account switch and refresh rotation invalidate stale write contexts. Missing cookies yield 204; invalid/expired sessions fail closed (409), rather than silently treating them as guest. The bridge uses explicit CORS, private no-store responses, bounded JSON bodies and a fixed upstream. Access expiry requires revisiting Console for normal refresh. The production shopping gate remains OFF until integrated browser and sandbox checkout qualification; in-flight revocation races, pending guest claims, UI adoption and account switching must still be tested. No schema change.

### Pending-invoice payment recovery
Existing single-domain purchases and combined carts share the canonical gateway/consent/receipt components. Customer-facing primary action is Pay now; prior-payment verification is secondary. An expired confirmed Paystack **test** attempt can be retried only after a positive authenticated readback of abandoned/failed, exact financial ownership/amount/currency and test scope, no signed success evidence, and revalidation under invoice/intent locks. ### Automatic server-side test payment reconciliation
Signed Paystack Test Mode notifications now reach the same test-only reconciliation dispatcher from webhook delivery and the authenticated daily Vercel worker. A verified current payment updates its test invoice/intent/order without operator approval. Private single-domain payments are recorded independently of supplier availability; the owner-scoped or UUID-pinned private registrar worker may subsequently reserve and submit a new registration once, with the existing claim and evidence guards. Public payments remain simulation-only. Completed historical test notifications are independently read back and audited as system activity (null actor), never replayed as supplier work, never backdated, and never represented as real money. New and historical work have separate two-event bounded retry lanes, prioritizing unattempted then least recently attempted notifications. Rejected/ambiguous proofs remain unprocessed and visible for optional intervention; duplicate or conflicting signed remote identities cannot settle a payment. The cron remains daily for compatibility with the current deployment plan; genuine webhook deliveries reconcile immediately. Live payment settlement is not enabled by this release. No migrations or credential changes.

The same scheduled worker refreshes the verification receipt of the *already approved*, exact current-version Paystack test binding after five days, using authenticated read-only provider evidence and the existing vault custody, audit-chain and database gates. New, revoked, rotated, unbound or live credentials are never approved automatically. This avoids an unnecessary weekly per-payment operator dependency without granting new credential or payment authority.
