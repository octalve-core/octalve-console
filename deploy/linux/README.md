# Independent Linux deployment profile

Templates, not an installed server. Use a supported Linux distribution, Python 3.12+, the repository's pinned Node/pnpm versions and PostgreSQL. Create a non-login octalve service account; install the reviewed checkout at /srv/octalve, virtualenv at /srv/octalve/.venv, install locked dependencies, build frontend with the intended production environment. Run the existing migration and deployment checks before starting services. Store environment files in /etc/octalve, root-owned mode 0600. Preserve existing application secrets, encryption keys, environment gates and MFA policies; never copy credentials into source. Configure HTTPS reverse proxy for the existing API and Console domains, validate host, CORS, CSRF and cookie settings and backups. No new supplier-specific keys are introduced.

The worker uses the existing CLOUD_COMMERCIAL_SCHEDULER_ENABLED setting. OCTALVE_WORKER_LISTEN_DSN must be a direct (not transaction-pooled) PostgreSQL connection to the same database, over authenticated TLS where remote. The application writes durable business records before best-effort lane-only PostgreSQL NOTIFY; notification loss is recovered by periodic scans. The listener never interprets customer or supplier inputs. Maximum two children; subprocess timeout 240s; six-minute lease for Linux children; HTTP lease 35 minutes to exceed the documented Vercel maximum of 30 minutes. Do not enable external HTTP scheduling concurrently with the Linux scheduler. Keep platform runtime duration under its lease, and verify it before activation. Existing provider, payment and destructive operation policies still apply.

Recovery intervals: payments/staging/provisioning/mail 5 min; renewals/cancellation hourly; lifecycle 30 min. Verified payment staging already runs after commit; new staged work wakes provisioning, new transactional outbox rows wake mail, applied renewals wake lifecycle. Linux workers restart on disconnect, and initial scans recover missed work. Backpressure limits remain; tune only after measured queue age and capacity. Vercel commercial profile retains polling because it has no persistent listener; daily temporary Vercel profile is unchanged.

Install units only after adapting paths, confirming binary locations and environment configuration. Use systemd-analyze verify on target, then daemon-reload and start the API, Console and worker. Inspect journal and Admin Cron jobs, measure queue age and exercise synthetic and then controlled real-provider acceptance. Verify backup/restore and reverse-proxy health before changing DNS. For migration, stop old scheduler, wait for in-flight workers/leases, preserve DB and vault, start new scheduler, verify heartbeat and reconcile uncertain operations before DNS cutover.

Each Linux child drains productive batches for at most eight iterations and checks a 90-second soft budget between batches; the supervisor still enforces the 240-second hard child timeout. Held lane executions retry after sixty seconds. A newly created domain challenge also wakes provisioning; DNS propagation may still require recovery polling.
